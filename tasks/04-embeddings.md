# 04. Семантический поиск по вики на эмбеддингах (CPU по умолчанию)

## Зачем

MCP-поиск по вики сейчас работает по ключевым словам и плохо отвечает на вопросы
своими словами. Замер на двух реальных вики (25 размеченных вопросов, 976 кусков):

| способ | правильная страница первой | в первой тройке |
|---|---|---|
| нынешний `search_docs` (ключевые слова) | 40% | 64% |
| эмбеддинги `intfloat/multilingual-e5-small` | 52% | 88% |

Цель: поиск в MCP по эмбеддингам с моделью `multilingual-e5-small`, которая
считается на процессоре в соседнем контейнере. Модель и адрес должны меняться
настройкой, без правок кода: позже на стенде с GPU поставят `Qwen3-Embedding-0.6B`,
у неё 80% и 92%.

Форк продолжает подтягивать апстрим. Поэтому весь новый код — в новых файлах, а
правки апстримных файлов — точечные: регистрация в DI, `DbSet`, SQL-блоки в
`DbInitializer`, вызов из MCP-инструментов.

## Как устроено (решения уже приняты)

- **Сервис эмбеддингов — отдельный контейнер** `ghcr.io/huggingface/text-embeddings-inference`
  в CPU-варианте, модель `intfloat/multilingual-e5-small`. Бэкенд ходит в его
  OpenAI-совместимый `POST {EMBEDDING_ENDPOINT}/embeddings`, тело
  `{"model": ..., "input": [...]}`. Тот же формат отдают LM Studio, Ollama и
  OpenAI, так что дома можно указать LM Studio. Других форматов не делать.
- **Векторы хранятся в БД**, в новой таблице. Поиск идёт перебором с косинусной
  близостью в памяти процесса. Векторную БД и расширения SQLite/Postgres не подключать.
- **Индексация — отдельный фоновый воркер, который опрашивает БД.** Хуков в
  генератор вики не добавлять: воркер сам находит страницы без векторов или с
  изменившимся текстом. Так он покрывает и новые, и обновлённые, и уже
  существующие вики, не трогая `WikiGenerator`.
- **Фича выключается сама.** Если `EMBEDDING_ENDPOINT` пуст или сервис недоступен,
  всё работает как раньше: воркер не индексирует, MCP ищет по ключевым словам.

## Что сделать

### 1. Настройки

Новый класс опций (по образцу существующих `*Options`), источник — переменные
окружения или `appsettings`:

| переменная | по умолчанию | смысл |
|---|---|---|
| `EMBEDDING_ENDPOINT` | пусто (фича выключена) | база OpenAI-совместимого API, например `http://embeddings:80/v1` |
| `EMBEDDING_MODEL` | `intfloat/multilingual-e5-small` | имя модели в запросе и в БД |
| `EMBEDDING_API_KEY` | пусто | если задан — заголовок `Authorization: Bearer` |
| `EMBEDDING_QUERY_PREFIX` | `query: ` | приписывается к тексту запроса (так требует e5) |
| `EMBEDDING_DOCUMENT_PREFIX` | `passage: ` | приписывается к тексту куска |
| `EMBEDDING_INDEX_INTERVAL_SECONDS` | `30` | пауза между проходами воркера |
| `EMBEDDING_BATCH_SIZE` | `32` | кусков в одном запросе |

Префиксы — именно настройки, а не код: у Qwen3 они другие.

### 2. Клиент эмбеддингов

Новый сервис `IEmbeddingClient` с методом «тексты → нормализованные векторы
`float[]`». Требования:

- `HttpClient` через `IHttpClientFactory`, таймаут 60 с;
- нормализация до единичной длины на нашей стороне: не все серверы нормализуют;
- при ошибке HTTP или сети — исключение с понятным текстом. Вызывающий код
  решает, что делать дальше.

### 3. Хранилище

Новая сущность `DocChunkEmbedding : AggregateRoot<string>` в
`src/OpenDeepWiki.Entities/Repositories/`:

- `DocFileId` (string, индекс);
- `BranchLanguageId` (string, индекс);
- `ChunkIndex` (int);
- `Text` (текст куска без префикса — для сниппета в выдаче);
- `ContentHash` (SHA-256 от `DocFile.Content` на момент индексации, hex);
- `Model` (string);
- `Dimensions` (int);
- `Vector` (`byte[]`, float32 little-endian).

Добавить по всем слоям **ровно тем путём, каким коммит `b753ee9` добавил
`WikiGenerationSlots`**: `IContext`, `MasterDbContext` (DbSet и конфигурация
модели), блоки `CREATE TABLE IF NOT EXISTS` и индексы в `DbInitializer` для
SQLite **и** для Postgres, EF-миграции для обоих провайдеров, если `b753ee9` их
добавлял. Сначала посмотреть `git show b753ee9 --stat` и повторить состав.

### 4. Нарезка

Чистая статическая функция (её покрывает тест):

- текст страницы делится по пустым строкам на абзацы;
- абзацы склеиваются, пока кусок не превысит ~1200 символов;
- абзац длиннее 1200 символов режется по границе предложения или строки,
  а если такой нет — жёстко по 1200;
- к каждому куску спереди добавляется строка с заголовком страницы
  (`DocCatalog.Title`);
- пустые куски не создаются.

### 5. Воркер индексации

`BackgroundService`, регистрируется через `AddHostedService` рядом с остальными.
Каждые `EMBEDDING_INDEX_INTERVAL_SECONDS`:

1. Если фича выключена — ничего не делать. Проверка дешёвая, лог не засоряем.
2. Найти страницы, которым нужна (пере)индексация: `DocFile` не удалён, текст не
   пустой, у него есть живой `DocCatalog` с `DocFileId`, и выполняется одно из:
   - у страницы нет векторов;
   - у её векторов другой `Model`;
   - её текст изменился.

   Изменение текста определять **без загрузки всех текстов на каждом проходе**.
   Сначала проверить, обновляется ли `DocFile.UpdatedAt` при каждой записи
   `Content`: найти все места, где пишется `DocFile.Content`, и указать их в
   отчёте. Если обновляется — сравнивать `UpdatedAt` с `CreatedAt` векторов в SQL.
   Если нет — сравнивать `ContentHash`, но загружать тексты пачками и только на
   проходах, когда SQL-кандидатов нет, не чаще раза в 10 минут. В отчёте написать,
   какой вариант выбран и почему.
3. Обработать за проход не больше 20 страниц: нарезать, получить векторы пачками
   по `EMBEDDING_BATCH_SIZE`, в одной транзакции удалить старые векторы страницы
   и вставить новые.
4. Удалить векторы страниц, которых больше нет (удалён `DocFile`).
5. Если сервис эмбеддингов недоступен — одно предупреждение в лог и пауза
   5 минут, без спама на каждом проходе.

Параллельно с генерацией вики воркер не должен мешать: он только читает
`DocFile`/`DocCatalog` и пишет в свою таблицу.

### 6. Поиск

Новый сервис `ISemanticDocSearch`:

- вход: текст запроса, набор `BranchLanguageId` (область поиска), `topK`;
- векторы области загружаются из БД, сравниваются с вектором запроса
  (запрос с `EMBEDDING_QUERY_PREFIX`), берутся только векторы текущей `Model`;
- **оценка страницы — максимум по её кускам**;
- выход: страницы по убыванию оценки, у каждой — `DocFileId`, оценка, текст
  лучшего куска;
- если фича выключена, сервис недоступен или в области нет векторов —
  вернуть признак «семантика недоступна» без исключения: вызывающий откатится
  на старый поиск.

### 7. MCP

- **`search_docs`** (глобальный, `MCP/McpGlobalTools.cs`): если семантика
  доступна — область из всех готовых репозиториев нужного языка (или из
  `owner`/`repo`, если заданы), выдача семантическая. Формат JSON-ответа прежний:
  те же поля у каждого результата (`owner`, `repo`, `branch`, `language`, `title`,
  `path`, `score`, `snippet` и т.д.). В `reason` для семантических результатов
  писать `"semantic"`, сниппет брать из лучшего куска. Если семантика
  недоступна — нынешний алгоритм без изменений.
- **`search_doc`** (репозиторный, `MCP/McpRepositoryTools.cs`): то же для одного
  репозитория. Старая ветка с `LIKE` остаётся откатом.
- **Язык по умолчанию.** Сейчас `language = "zh"` (глобальные) и `"en"`
  (репозиторные), а у вики, сгенерированных на других языках, поиск без явного
  языка ничего не находит. Сделать дефолтом `null`, что означает «любой язык»:
  у глобальных — искать по всем языкам; у репозиторных `search_doc` и
  `read_doc` — брать первый язык, для которого у ветки есть документы. Обновить
  тексты `Description` параметров.
- **Кириллица без экранирования.** Ответы MCP сериализуются с `\uXXXX` на
  каждую не-ASCII букву, и русский текст раздувается в 6 раз. Во всех
  `JsonSerializer.Serialize` в `MCP/McpGlobalTools.cs` и `MCP/McpRepositoryTools.cs`
  использовать опции с `JavaScriptEncoder.UnsafeRelaxedJsonEscaping` (одно общее
  поле с опциями на файл).

### 8. Compose

В `compose.yaml` и `compose.pgsql.yaml` добавить сервис `embeddings`:

- образ `ghcr.io/huggingface/text-embeddings-inference` в CPU-варианте. Закрепить
  конкретную версию, а не `cpu-latest`: узнать её из `GET /info` → `version` у
  `cpu-latest` или из релизов. Если не получилось — оставить `cpu-latest` и
  написать в отчёте;
- аргументы: `--model-id intfloat/multilingual-e5-small --auto-truncate`;
- том для кэша модели: `./data/hf-cache:/data`;
- порт наружу **не** публиковать;
- у `opendeepwiki` добавить `EMBEDDING_ENDPOINT=${EMBEDDING_ENDPOINT:-http://embeddings:80/v1}`
  и `EMBEDDING_MODEL=${EMBEDDING_MODEL:-intfloat/multilingual-e5-small}`;
- `depends_on` не делать жёстким: бэкенд должен стартовать, даже если embeddings
  ещё качает модель.

В `.env.example` добавить закомментированные переменные из раздела 1 с пояснением.
`compose.local.yaml` не трогать: его нет в git, его настрою сама.

## Чего не делать

- Не трогать `WikiGenerator`, генерацию, промпты, фронт.
- Не подключать справочник моделей админки (`AiModelConfigs`, тип `embedding`):
  это отдельная задача потом.
- Не прятать репозиторные инструменты из глобального MCP: тоже потом.
- Не добавлять векторные БД и расширения.
- Не менять формат ответов MCP сверх перечисленного.

## Тесты (xUnit, в `tests/OpenDeepWiki.Tests`)

- нарезка: длинный абзац, короткие абзацы склеиваются, заголовок в каждом куске,
  нет пустых кусков;
- сериализация вектора `float[] ↔ byte[]` туда-обратно без потерь;
- ранжирование `ISemanticDocSearch` на фальшивом `IEmbeddingClient` с заданными
  векторами: оценка страницы — максимум по кускам, порядок верный, векторы чужой
  `Model` игнорируются;
- воркер на БД в памяти (SQLite in-memory, если в тестах уже так делают; иначе как
  принято в проекте) с фальшивым клиентом:
  - индексирует новую страницу;
  - переиндексирует после изменения текста;
  - удаляет векторы удалённой страницы;
  - при недоступном клиенте ничего не ломает;
- MCP `search_docs` и `search_doc`: при доступной семантике `reason == "semantic"`
  и порядок из векторов; при недоступной — прежняя выдача;
- язык по умолчанию: вызов без `language` находит документы `ru`;
- JSON-ответ MCP содержит кириллицу как есть, без `\u04`.

## Ворота

.NET SDK на машине нет, всё запускать в контейнере `mcr.microsoft.com/dotnet/sdk:10.0`
**с копией** репозитория (`docker run --rm -v "<repo>:/src:ro" ... sh -c 'cp -r /src /w && cd /w && ...'`),
скрипт передавать через stdin (`docker run -i ... bash -s < script.sh`). Монтирование
одиночных файлов на этой машине зависает.

- `dotnet build src/OpenDeepWiki/OpenDeepWiki.csproj -c Release` — без ошибок.
- `dotnet test tests/OpenDeepWiki.Tests -c Release` — все новые тесты зелёные.
  Известные нестабильные и падающие до этой задачи тесты:
  - `AiProviderPresetSeederTests.Catalog_LoadsOpenCoworkBuiltInProviders`;
  - `RepositorySkillMarkdownBuilderTests.BuildSkillMarkdown_ShouldCreateEnglishDescriptorAndDocumentIndex`;
  - все `GraphifyCliRunnerTests.*`.

  От прогона к прогону они то падают, то нет. Кроме них падений быть не должно:
  привести список упавших.
- `docker compose -f compose.yaml config` — валиден.
- Фронт не трогается, его ворота не нужны.

Работающий стенд (контейнеры `opendeepwiki-local-*`, порты 8090/18081) **не
трогать**: не останавливать и не пересобирать. Приёмку на живых данных сделаю сама.
Коммитить не надо.

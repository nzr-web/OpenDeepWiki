# 04. Семантический поиск по вики на эмбеддингах (CPU по умолчанию)

## Зачем

MCP-поиск по вики работает по ключевым словам и плохо отвечает на вопросы своими
словами. Замер на двух реальных вики (25 размеченных вопросов, 976 кусков):

| способ | правильная страница первой | в первой тройке |
|---|---|---|
| нынешний `search_docs` (ключевые слова) | 40% | 64% |
| эмбеддинги `intfloat/multilingual-e5-small` | 52% | 88% |

Цель — поиск в MCP по эмбеддингам. По умолчанию модель `multilingual-e5-small`,
она считается на процессоре в соседнем контейнере. Модель и адрес меняются
настройкой без правок кода: позже на стенде с GPU поставят `Qwen3-Embedding-0.6B`.

Форк продолжает подтягивать апстрим. Поэтому новый код живёт в новых файлах, а в
апстримных файлах правки точечные: регистрация в DI, `DbSet`, SQL-блоки в
`DbInitializer`, ветка в MCP-инструментах, описания параметров.

## Принятые решения (не пересматривать)

- **Сервис эмбеддингов** — отдельный контейнер
  `ghcr.io/huggingface/text-embeddings-inference:cpu-1.9.4`. Бэкенд ходит в его
  OpenAI-совместимый `POST {EMBEDDING_ENDPOINT}/embeddings` с телом
  `{"model": ..., "input": [...]}`. Тот же формат у LM Studio, Ollama и OpenAI.
  Других форматов не делать.
- **Векторы хранятся в БД**, в новой таблице. Поиск — перебор в памяти с
  косинусной близостью. Векторные БД и расширения не подключать.
- **Индексация** — отдельный фоновый воркер, опрашивающий БД. В `WikiGenerator`
  хуков не добавлять.
- **Изменение страницы определяется по `DocFile.UpdatedAt`.** Проверено: все
  места записи `DocFile.Content` вызывают `UpdateTimestamp()`
  (`DocTool.cs` Write/Append/Edit, `AdminRepositoryService.cs` ручная правка).
  Новые страницы создаются с `UpdatedAt = null`. Ветку с хешированием всех
  текстов не делать.
- **Фича выключается сама.** Пустой `EMBEDDING_ENDPOINT` означает, что всё
  работает как раньше: воркер не индексирует, MCP ищет по ключевым словам.
- **Справочник моделей админки** (`AiModelConfigs`, тип `embedding`) **не
  подключать** — это отдельная задача.
- **Документацию в `docs/` не трогать.**

## Определения

- **Живая страница** — `DocFile` с `IsDeleted == false`, у которого `Content` не
  пустой и не из одних пробелов, и есть хотя бы один `DocCatalog` с
  `IsDeleted == false` и `DocFileId == DocFile.Id`. Один и тот же предикат
  используется везде: при поиске кандидатов на индексацию, при удалении
  векторов и при поиске.
- **Отметка источника** страницы — `DocFile.UpdatedAt ?? DocFile.CreatedAt`.

## Что сделать

### 1. Настройки

Новый класс `EmbeddingOptions` в новом файле. Значения читаются так же, как в
`WikiGeneratorOptionsConfigurator`: плоские имена из `IConfiguration` в
`PostConfigure`. Секция `Embedding` в appsettings может их переопределять.

| переменная | по умолчанию | смысл |
|---|---|---|
| `EMBEDDING_ENDPOINT` | пусто = выключено | база API, например `http://embeddings:80/v1` |
| `EMBEDDING_MODEL` | `intfloat/multilingual-e5-small` | имя модели в запросе и в БД |
| `EMBEDDING_API_KEY` | пусто | если задан, отправляется заголовок `Authorization: Bearer …` |
| `EMBEDDING_QUERY_PREFIX` | `query: ` | приписывается к тексту запроса |
| `EMBEDDING_DOCUMENT_PREFIX` | `passage: ` | приписывается к тексту куска |
| `EMBEDDING_INDEX_INTERVAL_SECONDS` | `30` | пауза между проходами воркера |
| `EMBEDDING_BATCH_SIZE` | `32` | кусков в одном запросе |

### 2. Клиент `IEmbeddingClient`

Метод «список текстов → список нормализованных `float[]` того же порядка».

- `HttpClient` через `IHttpClientFactory`, таймаут 60 с.
- Ответ сортировать по полю `index` из `data[]`: сервер вправе вернуть элементы
  не по порядку.
- Каждый вектор нормализовать до единичной длины на нашей стороне.
- При HTTP-ошибке, ошибке сети или неверном формате ответа — исключение с
  текстом, где есть код ответа и адрес.
- Если фича выключена, клиент не создаёт `HttpClient` и не вызывается вовсе.
  Это проверяют вызывающие, см. разделы 5 и 6.

### 3. Хранилище

Новая сущность `DocChunkEmbedding : AggregateRoot<string>` в
`src/OpenDeepWiki.Entities/Repositories/`:

| поле | тип |
|---|---|
| `DocFileId` | string, индекс |
| `BranchLanguageId` | string, индекс |
| `ChunkIndex` | int |
| `Text` | текст куска без префикса, для сниппета |
| `ContentHash` | hex SHA-256 от `Content` на момент индексации, для диагностики |
| `SourceStamp` | DateTime: отметка источника, прочитанная **до** нарезки |
| `Model` | string |
| `Dimensions` | int |
| `Vector` | `byte[]`, float32 little-endian |

Подключить так же, как коммит `b753ee9` подключил `WikiGenerationSlots`:

- `IContext` и `MasterDbContext`: `DbSet` и конфигурация модели;
- **тестовые контексты, реализующие `IContext`** (`TestDbContext`,
  `TestConfigDbContext` и любые другие — найти все): добавить `DbSet`, иначе
  проект тестов не соберётся;
- `DbInitializer`: блоки `CREATE TABLE IF NOT EXISTS` и индексы для SQLite (в
  `MigrateSqliteAsync`) **и** Postgres (в `MigratePostgresqlAsync`), со всеми
  колонками `AggregateRoot`, включая `Version`. `Vector` — `BLOB` / `BYTEA`, даты
  в Postgres — `TIMESTAMP WITH TIME ZONE`. Смотреть на блок `WikiGenerationSlots`;
- EF-миграции — по одному написанному вручную `.cs` на провайдера, **без
  Designer-файлов и без правки `*ModelSnapshot.cs`**, как в `b753ee9`.
  `dotnet ef` не использовать.

### 4. Нарезка

Чистая статическая функция, `internal`, видимая тестам:

- текст делится по пустым строкам на абзацы;
- абзацы склеиваются, пока кусок не превысит 1200 символов;
- абзац длиннее 1200 символов режется по последней границе предложения
  (`. `, `! `, `? `) или строки в пределах 1200, а если её нет — жёстко по 1200;
- к каждому куску спереди добавляется строка с заголовком страницы;
- пустые и пробельные куски не создаются;
- текст не теряется: склейка всех кусков без заголовков равна исходному тексту
  с точностью до пробельных символов.

Заголовок берётся из `DocCatalog.Title`. Если у файла несколько каталогов —
из первого по `Order`, затем по `Id`.

### 5. Воркер индексации

`BackgroundService` в новом файле, регистрируется `AddHostedService` рядом с
остальными. Как и `BranchGenerationWorker`, на каждый проход создаёт новый scope
и берёт из него `IContext`.

На каждом проходе:

1. Фича выключена — выйти. Ни логов, ни HTTP.
2. Если идёт пауза после сбоя (п. 6) — выйти.
3. **Кандидаты** — живые страницы, для которых выполняется одно из условий:
   - векторов нет;
   - у векторов другой `Model`;
   - отметка источника больше сохранённого `SourceStamp`.

   Отбор целиком в SQL, без загрузки `Content` всех страниц. Не больше
   **20 страниц** за проход.
4. Для каждой страницы:
   1. прочитать `Content`, `Title` и отметку источника;
   2. нарезать;
   3. **вне транзакции** получить векторы пачками по `EMBEDDING_BATCH_SIZE` с
      префиксом документа;
   4. открыть транзакцию через `(context as DbContext)?.Database.BeginTransactionAsync()`.
      Если провайдер её не поддерживает (InMemory), работать без неё;
   5. удалить старые векторы страницы и вставить новые с прочитанным в п. 1
      `SourceStamp`, закоммитить.

   Если страница изменилась во время запроса к модели, её `UpdatedAt` окажется
   больше сохранённого `SourceStamp`, и следующий проход переиндексирует её.
   Правка не теряется.
5. **Удалить векторы** всех `DocFileId`, которые больше не живые страницы:
   файл удалён физически или мягко, текст опустел, каталоги удалены или
   отвязаны.
6. **Сбой.** Любое исключение клиента — пауза 5 минут: одно `Warning` в лог,
   проходы в паузе ничего не делают. На первом успешном проходе после паузы —
   одно `Information` «сервис эмбеддингов снова доступен».

### 6. Поиск `ISemanticDocSearch`

- Вход: текст запроса, набор `BranchLanguageId` (область), `topK`.
- Возвращает либо «недоступно», либо страницы по убыванию оценки. У каждой
  страницы: `DocFileId`, `BranchLanguageId`, оценка (косинус) и текст лучшего куска.
- **«Недоступно»** (без исключения), если выполняется одно из:
  - фича выключена (HTTP при этом не делается);
  - клиент бросил исключение;
  - в области меньше **90%** живых страниц проиндексировано текущей `Model`.

  Порог принят сознательно: частично проиндексированная вики семантикой хуже
  ключевого поиска, она молча теряет страницы. После смены модели вики какое-то
  время ищется по ключевым словам, пока воркер не переиндексирует. Это ожидаемо.
- Из БД загружаются только `Id`, `DocFileId`, `BranchLanguageId`, `Dimensions`,
  `Vector` векторов текущей `Model` в области. **`Text` не загружается**, он
  дочитывается только для лучших кусков отобранных топ-K страниц.
- Векторы, у которых `Dimensions` не равен длине вектора запроса, пропускаются
  без исключения.
- Оценка страницы — **максимум** по её кускам. Сниппет — текст того самого куска.
- Запрос отправляется с `EMBEDDING_QUERY_PREFIX`.

### 7. MCP

Сервис передаётся в инструменты необязательным параметром
`ISemanticDocSearch? semanticSearch = null`. Он стоит **после** последнего
содержательного параметра и перед `CancellationToken`. `null` значит
«семантика недоступна». Существующие позиционные вызовы в тестах должны
компилироваться без правок. Сервис зарегистрировать в DI так, чтобы MCP SDK
подставил его в инструменты.

**`search_docs`** (глобальный, `McpGlobalTools.cs`):

- если семантика доступна: область — все готовые репозитории (или
  `owner`/`repo`, если заданы) с языком `language` (при `null` — все языки);
- выдача семантическая, **дедуплицированная** по `(owner, repo, path)` с лучшей
  оценкой;
- поля каждого результата прежние, со значениями:
  - `Score = (int)Math.Round(cosine * 1000)`;
  - `MatchedTokenCount = 0`;
  - `FullQueryMatched = false`;
  - `Reason = "semantic"`;
  - `snippet` — из лучшего куска;
- `routedRepositories` — репозитории, из которых пришли результаты, в формате
  прежних элементов;
- `maxRepositories` в семантической ветке игнорируется;
- если семантика недоступна — нынешний алгоритм без изменений.

**`search_doc`** (репозиторный, `McpRepositoryTools.cs`):

- семантика по ветке и языку этого репозитория;
- в элементах `results` в семантической ветке добавить поля `score` (косинус,
  округлённый до 3 знаков) и `reason: "semantic"`, `matchLine = 0`;
- `summary` строится как раньше, через `BuildSearchSummaryAsync` из семантических
  `matches`;
- откат — нынешняя ветка с `LIKE`;
- выбор языка и выборку страниц вынести в небольшие `internal static` методы и
  тестировать их. MCP-обёртку `search_doc` целиком тестами не покрывать: ей нужны
  `AgentFactory`, `McpServer` и т.п.

**Язык по умолчанию.** Сейчас `"zh"` у глобальных и `"en"` у репозиторного, а
у вики на других языках поиск без явного языка ничего не находит.

- `search_docs`, `search_repositories`, `read_doc` (глобальные): дефолт `null`,
  что значит «любой язык». У `read_doc` пустой язык уже означает «любой», так
  что меняется только дефолт.
- `search_doc` (репозиторный): `null` → первый `BranchLanguage` ветки, у которого
  есть `DocCatalog` с непустым `DocFileId`. Порядок: сначала `IsDefault`, если
  такое поле есть, затем `LanguageCode` по алфавиту.
- Поле `language` в ответах — фактически использованный язык; при поиске по
  всем языкам — `null`.
- Обновить тексты `Description` всех четырёх параметров `language`, а
  `Description` у `search_docs` — так, чтобы он не утверждал, что поиск всегда
  идёт через маршрутизацию по репозиториям.

**Кириллица без экранирования.**

- `McpGlobalTools.cs`: в **существующее** поле опций добавить
  `Encoder = JavaScriptEncoder.UnsafeRelaxedJsonEscaping`, второе не заводить.
- `McpRepositoryTools.cs`: завести поле опций **только** с этим `Encoder`, без
  `PropertyNamingPolicy` (имена полей не должны измениться), и передавать его во
  все `JsonSerializer.Serialize`.

- том `./data/hf-cache:/data`;

строкой пояснения у каждой. `compose.local.yaml` не трогать, его нет в git.

## Тесты (xUnit, `tests/OpenDeepWiki.Tests`)

Тесты с транзакциями и удалением — на **настоящем SQLite** через
`SqliteDbContext` (файл во временной папке или `Data Source=:memory:` с открытым
соединением), а не на `TestDbContext` (InMemory). Смотреть на `DbInitializerTests`.

**Нарезка.** Входы:
- три абзаца по 500 символов;
- один абзац 3000 символов без точек;
- один абзац 3000 символов с предложениями;
- пустая и пробельная страница.

Проверки:
- каждый кусок не длиннее `1200 + длина заголовка + 1`;
- заголовок есть в каждом куске;
- склейка без заголовков равна исходнику с точностью до пробелов;
- для пустой страницы — 0 кусков.

**Вектор.** `float[] ↔ byte[]` туда-обратно без потерь.

**Клиент** (стаб `HttpMessageHandler`):
- тело запроса содержит `model` и `input`;
- `Authorization` есть при ключе и отсутствует без ключа;
- нормы векторов равны 1;
- ответ с перепутанным `index` возвращается в порядке входа;
- 500 и сетевая ошибка — исключение с кодом и адресом.

**Поиск** (фальшивый клиент с заданными векторами):
- страница A с кусками косинуса 0.9 и 0.1, страница B с четырьмя кусками по 0.5:
  A первой, сниппет A от куска 0.9;
- вектор чужой `Model`, идеально совпадающий с запросом, игнорируется;
- вектор другой размерности пропускается без исключения;
- покрытие области ниже 90% даёт «недоступно»;
- выключенная фича даёт «недоступно» и ни одного вызова клиента;
- в запрос ушёл `EMBEDDING_QUERY_PREFIX`;
- проекция загрузки векторов не включает `Text`.

**Воркер** (SQLite, фальшивый клиент со счётчиком вызовов):
- новая страница индексируется, в куски ушёл `EMBEDDING_DOCUMENT_PREFIX`;
- **второй проход без изменений не вызывает клиент**;
- изменение `Content` через `UpdateTimestamp()` ведёт к переиндексации: старые
  векторы удалены, `ContentHash` соответствует новому тексту;
- изменение во время запроса: фальшивый клиент внутри вызова меняет страницу с
  `UpdateTimestamp()`. Следующий проход переиндексирует её;
- **клиент не вызывается внутри транзакции**: фальшивый клиент проверяет
  `Database.CurrentTransaction == null`;
- 25 страниц — после одного прохода проиндексировано 20;
- 70 кусков при `EMBEDDING_BATCH_SIZE=32` — 3 вызова клиента;
- удаление: мягко удалённый файл, опустевший текст, удалённый каталог — векторы
  удалены;
- сбой клиента — за два прохода подряд клиент вызван один раз (пауза
  соблюдается);
- выключенная фича — ни одного вызова.

**DbInitializer** (по образцу существующих тестов): на SQLite-базе без таблицы
`InitializeAsync` её создаёт.

**MCP** (глобальные инструменты):
- `search_docs` с фальшивым семантическим сервисом на трёх и больше страницах в
  порядке, противоположном ключевому: порядок из векторов, `reason == "semantic"`,
  `score` по формуле, дубли по языкам схлопнуты;
- `semanticSearch == null` — выдача совпадает с прежней, существующие тесты
  проходят без правок;
- вызов без `language` находит документы `ru` (`search_docs`, `read_doc`);
- выбор языка репозиторного `search_doc` (internal-метод) — по правилу из п. 7;
- JSON-ответы обоих файлов (включая ошибку с кириллицей в `message`) содержат
  кириллицу как есть, без `\u04`. Множество имён полей не изменилось по
  сравнению с прежним.

## Ворота

.NET SDK на машине нет. Всё запускать в контейнере `mcr.microsoft.com/dotnet/sdk:10.0`
с **копией** репозитория:
`docker run --rm -i -v "C:/Users/Nazar/Работа/OpenDeepWiki:/src:ro" mcr.microsoft.com/dotnet/sdk:10.0 bash -s < script.sh`,
внутри `cp -r /src /w && cd /w && rm -rf web/node_modules`. Скрипт передавать
через stdin: монтирование одиночных файлов на этой машине зависает. Перед
запуском ставить `MSYS_NO_PATHCONV=1`.

1. **До правок**: `dotnet test tests/OpenDeepWiki.Tests -c Release` — сохранить
   список упавших (базовая линия).
2. `dotnet build src/OpenDeepWiki/OpenDeepWiki.csproj -c Release` — без ошибок.
